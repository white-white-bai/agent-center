# 智能体中台（Agent Center）概要设计

> 版本：v0.3（草案，技术栈定为 Python 单栈）
> 关联系统：`gov-service-ai-assistant`（区级智能客服、边聊边办、公共资源交易智能客服等）
> 目标读者：产品、架构、后端、前端、算法、运维

---

## 1. 背景与问题

现有 `gov-service-ai-assistant` 以 Dify Chatflow 为核心承载各政务场景的智能客服：

| 场景 | 现状载体 |
| --- | --- |
| 区级智能客服（多区） | Dify Chatflow + 区级知识库 |
| 边聊边办 | Dify Chatflow + 业务接口编排 |
| 公共资源交易智能客服 | Dify Chatflow + 交易知识库 |
| 日志分析 / 审批助手 | Dify Chatflow |

随着场景增多，暴露出结构性问题：

1. **知识孤岛**：知识按 chatflow 划分，跨场景无法复用，政策法规类共性知识重复维护、口径不一致。
2. **多轮对话能力弱**：chatflow 本质是固定流程图，缺少槽位管理、指代消解、话题切换、澄清追问等会话状态机能力。
3. **上下文与记忆缺失**：无法沉淀跨会话的用户事实、偏好与办理进度，"每次都是第一次见面"。
4. **提示词管理粗放**：提示词散落在各 DSL 中，无版本、无灰度、无评测、无回滚。
5. **无工具抽象**：业务接口硬编码在流程节点里，无法按需发现、鉴权、限流、审计，也不支持 MCP。
6. **无法协同**：多业务 Agent 之间没有路由与交接机制，只能靠用户自己选入口。
7. **无用户画像**：无法基于身份、历史行为做个性化回答与主动服务。
8. **不可观测**：一次回答经过了哪些步骤、调用了哪些工具、花了多少 token，无法追踪与评估。

**本项目的定位**：新建独立的中台系统 `agent-center`，提供 Agent 的定义、编排、运行时、记忆、画像、知识与工具能力，向上支撑各业务客服与边聊边办场景，替代"一个场景一个 chatflow"的模式。

## 2. 目标与非目标

### 2.1 目标

用工程能力落地 Agent 的六个特征：

| 特征 | 工程落地 |
| --- | --- |
| 自主性 | 目标驱动的 ReAct 循环：规划 → 调工具 → 观察 → 反思 → 继续/结束，而非固定流程 |
| 反应性 | 工具结果、业务事件、用户打断都能改变执行路径 |
| 规划性 | 任务分解、子目标管理、步骤预算与终止条件 |
| 主动性 | 主动澄清、主动补全槽位、主动提醒（办理进度、材料缺失） |
| 社会性 | 总管 Agent 分派 + 专业 Agent 交接 + 并行分工 + 评审 |
| 目标导向 | 每个 Agent 显式声明目标、约束、成功判定与兜底策略 |

同时补齐：

- 多轮会话状态机（槽位、指代、话题栈、澄清）
- 提示词分层管理与版本化
- 上下文装配与预算控制
- 分层记忆（工作/情节/语义/程序）与用户画像
- 统一工具层（MCP Server / Function Call / OpenAPI 导入）
- 统一知识湖与域路由（解决知识孤岛）
- 全链路 Trace、成本统计、离线评测与 badcase 回流

### 2.2 非目标（首期）

- 不训练/微调基础模型，仅做接入与路由。
- 不一次性下线全部 Dify chatflow，采用并行与逐步迁移。
- 不做通用低代码工作流编排器（复杂长流程仍可由业务系统承载，Agent 只负责交互与决策）。

### 2.3 非功能需求（首期目标值，待压测校准）

| 维度 | 指标 |
| --- | --- |
| 首 token 延迟 | P95 ≤ 2s（不含工具调用） |
| 单轮端到端延迟 | P95 ≤ 8s（含 1~2 次工具调用）；超过 15s 必须发送进度事件 |
| 可用性 | 核心对话链路 ≥ 99.9%；LLM 或工具单点故障不得导致整站不可用 |
| 并发 | 首期按日活 10 万、峰值并发会话 2000 设计，支持水平扩展 Runtime 实例 |
| 数据驻留 | 模型调用与用户数据均在政务云内闭环，见第 12 节"模型来源" |
| 租户隔离 | 会话、记忆、画像、知识检索全部带 `tenant_id` 过滤，查询层强制注入 |
| 可追溯 | 任一回答可反查 Run、工具调用、引用文档与所用提示词版本 |

## 3. 总体架构

### 3.1 分层视图

```
┌──────────────────────────────────────────────────────────────────────┐
│ 接入层   Web 客服窗口 / H5 / 小程序 / 数字人 / 12345 热线 / 第三方 API  │
└───────────────────────────────┬──────────────────────────────────────┘
                                │ HTTPS + SSE
┌───────────────────────────────▼──────────────────────────────────────┐
│ Agent 服务（Python 3.11 + FastAPI，单体部署，多实例水平扩展）           │
│  · 会话状态机   · ReAct/Plan 执行器   · 多 Agent 图编排（Supervisor）  │
│  · 上下文装配   · 记忆读写   · 工具调用（MCP Client / Function Call）  │
│  · 流式输出     · Trace 埋点                                          │
│  · 管理 API：Agent/提示词/工具/知识域/路由/模型的 CRUD 与发布          │
│  · 运营 API：会话查询、Trace、评测、报表、badcase                      │
└───────┬───────────────┬───────────────┬───────────────┬──────────────┘
        │               │               │               │
┌───────▼─────┐ ┌───────▼─────┐ ┌───────▼─────┐ ┌───────▼─────┐
│ LLM 网关    │ │ 工具中心     │ │ 知识与记忆   │ │ 外部系统     │
│ 多模型/路由 │ │ MCP/HTTP    │ │ 向量库/知识湖│ │ 业务接口/工单│
└─────────────┘ └─────────────┘ └─────────────┘ └─────────────┘

数据层：MySQL（元数据/会话/画像） · Redis（缓存/锁/限流） · 向量库 · 对象存储 · ES（全文检索）
```

**集成说明**：鉴权、敏感词、审计等能力通过 HTTP 调用现有平台接口获取，不在本服务内嵌入 kdsoft。Agent 服务对外提供 HTTPS + SSE 接口，前端与业务系统直接访问，不经过额外的 Java 网关层。

### 3.2 技术栈决策

- **单栈 Python**：Agent 能力（状态机、ReAct 循环、图编排、MCP、流式、评测）集中在一个服务内，Agent 生态（LangGraph、MCP SDK、LiteLLM）在 Python 侧最成熟。
- **管理面并入同一服务**：配置类 CRUD 与发布功能量小，不值得为其单独维护一套 Java 服务。
- **依赖现有平台的治理能力**：鉴权、敏感词、审计通过 HTTP 对接；若接口不可用，见第 9.1 节降级策略。

备选方案（已弃用）：双栈（Java 管理面 + Python 执行面）。管理面功能量小，双栈的部署与接口维护成本不划算。

### 3.3 技术选型

| 方向 | 选型 |
| --- | --- |
| 服务框架 | Python 3.11 + FastAPI（执行面与管理面共用） |
| 执行面 | LangGraph（图编排）+ LiteLLM（多模型统一） |
| 流式协议 | SSE（`text/event-stream`） |
| 元数据/会话 | MySQL 8 |
| 缓存/分布式锁/限流 | Redis |
| 向量检索 | Milvus（或 pgvector，视数据规模） |
| 全文检索 | Elasticsearch（混合检索 BM25 + 向量） |
| 对象存储 | MinIO / 现有文件中心 |
| 可观测 | OpenTelemetry + Prometheus + 结构化日志 |
| 数据库访问 | SQLAlchemy 2.x + Alembic（迁移） |
| 管理页面 | Vue3 + Element Plus（沿用现有前端技术栈，仅作为 Python 服务的静态前端） |

## 4. 核心领域模型

### 4.1 Agent 定义

```
Agent
├─ 基本信息：id / code / 名称 / 所属域 / 租户
├─ 角色：role、人设、边界（能做什么、不做什么）
├─ 目标：goal、成功判定（success_criteria）、约束（constraints）
├─ 提示词：绑定 prompt_template（版本化）
├─ 知识：knowledge_scopes（域/空间/标签）
├─ 工具：tool_ids、工具调用上限、是否需人工确认
├─ 模型：model_policy（主模型、降级模型、温度、最大步数）
├─ 记忆：memory_policy（读写哪些记忆类型、TTL）
├─ 路由：router_rules（何时被总管选中、何时交接出去）
├─ 兜底：fallback（转人工、澄清、拒绝话术）
└─ 生命周期：draft → published → deprecated
```

Agent 组织为 **域（Domain）**：区级客服域、边聊边办域、公共资源交易域、日志分析域。域之间共享平台级知识，隔离私有知识。

### 4.2 多 Agent 角色划分

| 角色 | 职责 |
| --- | --- |
| 总管 Agent（Supervisor） | 意图识别、分派、汇总、兜底；只做协调不做具体业务 |
| 业务 Agent | 域内问答（区客服、公共资源交易等） |
| 事务 Agent | 边聊边办：槽位收集、执行工具、确认与回执 |
| 知识 Agent | 政策检索与引用溯源 |
| 评审 Agent（Critic） | 对高风险回答做合规/事实校验（可选） |

## 5. 关键子系统设计

### 5.1 会话与上下文管理

**四层数据结构**：`Conversation → Turn → Message → Run`

- `Conversation`：一次会话，绑定用户、渠道、Agent 组、状态（进行中/结束/转人工）。
- `Turn`：用户一问 + 系统一答（可能包含多个 Run）。
- `Message`：单条消息（用户/助手/工具/系统），含 token、引用、附件。
- `Run`：一次 Agent 执行轨迹，`run_step` 记录 thought / action / observation / 耗时 / 成本，用于回放与评测。

**上下文装配流水线**（按优先级填充，超预算时从低优先级裁剪）：

```
系统基线（平台安全与风格）
  → Agent 人设与目标
  → 用户画像摘要（身份/偏好/在办事项）
  → 长期记忆检索结果（Top-K，去重）
  → 知识与工具召回结果
  → 会话滚动摘要
  → 最近 N 轮原文（含工具结果摘要）
  → 本轮用户输入 + 会话状态（槽位、话题栈）
```

**多轮对话能力**：

- 槽位（Slot）管理：目标必填项、已填/缺失、来源（用户/画像/知识）。
- 指代消解：结合话题栈与槽位解析"它/这个/上次那个"。
- 话题栈：支持插话（"顺便问一下"）后回到原话题。
- 澄清策略：低置信度必修必填槽位缺失时主动追问，最多 N 次后转人工。
- 打断与重生成：用户可在 Run 执行中打断。

**预算控制**：按模型上下文窗口计算可用预算，预留输出 token 与工具结果空间；超限触发摘要压缩与二阶段裁剪。

### 5.2 记忆系统

| 类型 | 内容 | 存储 | 生命周期 |
| --- | --- | --- | --- |
| 工作记忆 | 当前 Run 的中间状态、工具结果 | Runtime 内存/Redis | 单次 Run |
| 情节记忆 | 会话事件（问过什么、办过什么、结果） | MySQL + 向量 | 按会话保留周期 |
| 语义记忆 | 稳定事实与偏好（"我在常州天宁区"、"习惯看办事指南"） | 结构化表 + 向量 | 长期，可更新 |
| 程序记忆 | 成功完成任务的工具链/SOP | MySQL（模板化）+ 向量 | 长期，可复用 |

**写入策略**：每轮结束后异步抽取候选记忆 → 重要度/新近度/置信度打分 → 与已有记忆去重合并 → 冲突时以时间新、来源权威为准，并保留历史版本。
**读取策略**：按当前意图与槽位做混合检索（向量 + 关键词 + 结构化过滤），只注入与当前任务相关的少量条目，避免污染上下文。
**隐私与合规**：用户可查、可删；敏感字段脱敏存储；TTL 可配置；删除走级联清理（含向量库）。

### 5.3 用户画像

三层结构：

1. **身份属性**：实名信息、区域、企业/个人、证件类型（与业务库同步，脱敏）。
2. **行为标签**：高频事项、咨询主题、办理阶段、投诉历史（离线 + 实时打标）。
3. **交互偏好**：回答详略、语言风格、渠道偏好、无障碍需求。

画像服务提供：`getProfile(userId)`、`mergeTags(userId, tags)`、`getActiveMatters(userId)`。
画像在运行时以"摘要卡"注入提示词，而不是原始标签全量塞入，控制 token。
标签需可解释（来源、时间、置信度），并支持人工纠偏。

### 5.4 提示词管理

- **结构**：`角色 / 目标 / 边界与约束 / 工具使用规范 / 输出格式（JSON Schema）/ 示例 / 安全规则`。
- **变量**：`{{user.profile}}`、`{{session.slots}}`、`{{knowledge.snippets}}`、`{{tools}}`，由上下文装配器填充。
- **分层继承**：平台基线 → 域模板 → Agent 模板 → 场景覆盖（后者覆盖前者，不复制粘贴）。
- **版本与环境**：草稿/发布版本、dev/test/prod 环境绑定、灰度比例、AB 实验、一键回滚。
- **评测闭环**：每次发布必须跑评测集（准确性、引用正确率、合规、平均步数/成本），badcase 自动入集。

### 5.5 工具与 MCP

**统一工具描述**：名称、语义说明、入参/出参 JSON Schema、鉴权方式、限流、超时、幂等键、是否需要用户确认、审计级别。

**来源**：

1. MCP Server（标准协议，远程工具，支持 SSE/stdio 传输）。
2. Function Call（中台内部 Python 函数或内部 HTTP 服务，注册即可用）。
3. OpenAPI 导入（现有业务接口，自动生成工具描述）。
4. 系统内置：知识检索、画像查询、会话管理、转人工、表单填充。

**执行循环**（ReAct）：

```
规划 Plan → 选择工具 → 参数校验 → 权限/限流检查 → 执行（超时/重试/幂等）
  → 结果规范化 → 观察 Observe → 反思 Reflect → 继续 / 结束 / 澄清 / 转人工
```

**约束**：最大步数、最大工具调用次数、单次 token 预算、工具白名单按 Agent 与用户角色双重控制、写操作（提交表单/发短信）必须二次确认、工具调用全程留痕。
**权限透传**：以最终用户身份调用（OAuth2/Token 透传），禁止用系统超管身份调用业务接口。

**工具治理默认值**（可在 Agent 或工具级覆盖）：

| 项 | 默认值 | 说明 |
| --- | --- | --- |
| 单次工具超时 | 5s（查询类）/ 10s（写操作） | 超时不自动重试写操作 |
| 重试 | 查询类最多 2 次，指数退避 200ms 起 | 仅对网络错误与 5xx 重试 |
| 熔断 | 同一工具 30s 内失败率 > 50%（且样本 ≥ 10）时熔断 60s | 熔断期间直接返回降级结果 |
| 写操作幂等 | 必须携带 `Idempotency-Key`（由 `run_id + tool_code + 规范化参数哈希` 生成） | 业务侧需支持幂等，否则该工具不允许注册为写操作 |
| 写操作确认 | 展示"将为你提交：…"摘要，用户明确回复确认后才执行 | 确认记录写入 `run_step` |

**工具结果的安全处理**：工具返回内容作为数据注入上下文，并包裹为不可信区块（如 `<tool_result untrusted="true">…</tool_result>`），由提示词安全规则约束其不得覆盖系统指令。

### 5.6 知识协同

- **知识湖**：统一入库、统一切分、统一元数据（来源、发文机关、生效/失效日期、适用区域、权威等级）。
- **三层可见性**：平台共享层（政策法规、办事指南）→ 域层（区、交易、审批）→ Agent 私有层（话术、FAQ）。
- **路由式检索**：总管识别业务域 → 域内检索 → 无结果时全域兜底 → 结果按时效/地域/权威度重排。
- **冲突消解**：同一问题多个口径时，按"生效时间新 > 发文层级高 > 适用区域匹配"选择，并显式说明依据。
- **可溯源**：回答附引用（文档名、条款、更新时间），支持前端点击查看原文。
- **知识同步**：与现有 knowflow/Dify 知识库对接，支持增量同步与断点续传；同步失败可回滚。

### 5.7 多 Agent 协同

**编排模式**：

| 模式 | 说明 | 适用 |
| --- | --- | --- |
| Supervisor 分派 | 总管解析意图，选一个专业 Agent 执行并汇总 | 主路径 |
| Handoff 交接 | Agent 之间移交控制权，携带上下文与槽位 | 跨域连续办事 |
| Fan-out / Reduce | 并行调用多个 Agent 或工具，汇总结果 | 复杂查询、多区对比 |
| Critic 复核 | 高风险回答由评审 Agent 校验后再输出 | 政策解读、金额相关 |

**协作契约**：

- 共享黑板：Session Context（会话状态、槽位、画像摘要、已用工具结果）只读共享，写入需仲裁。
- 任务消息：`Task{goal, inputs, constraints, deadline}` → `TaskResult{status, output, evidence, usage}`。
- 交接协议：明确交接原因、已确认事实、待办槽位、禁止重复提问项。

**执行预算默认值**（按 Agent 的 `model_policy` 与 `fallback` 配置覆盖）：

| 项 | 默认值 |
| --- | --- |
| 单 Run 最大步数（LLM 决策轮次） | 8 |
| 单 Run 最大工具调用次数 | 6 |
| 单 Run 最大耗时 | 30s |
| 单 Run 最大 token（输入+输出） | 32k |
| 同一槽位最多澄清次数 | 2，之后转人工或给出"可办理范围"说明 |
| 单会话连续澄清/失败轮次 | 3，超出即转人工 |
| Handoff 最大跳数 | 3，防止 Agent 之间循环交接 |

**终止与兜底**：步数/时间/成本预算耗尽、连续失败、置信度低 → 输出澄清问题或转人工，并附带已完成信息，避免用户重复描述。转人工时将会话摘要、槽位与已调用工具结果一并推送至坐席工作台。

**多 Agent 并行的一致性**：Fan-out 子任务只读共享黑板；子任务结果由 Reduce 节点统一汇总，不允许子任务直接写入会话状态。同一会话同一时刻只允许一个 Run 处于写状态（会话级分布式锁，Redis）。

### 5.8 边聊边办（事务型 Agent）

- 槽位驱动：事项 → 表单字段 → 从画像/历史复用 → 逐项确认。
- 执行前置：展示"将为你提交：xxx"，明确征得同意。
- 幂等与补偿：提交携带幂等键，失败可重试，超时回查。
- 进度回写：办理状态进入事件流，可主动推送（主动性）。
- 风险控制：金额、证件号等敏感操作二次校验，关键节点转人工。

### 5.9 主动性机制

- 主动澄清：信息不足时先问再答。
- 主动提醒：在办事项到期、材料缺失、政策变更（由定时任务/事件驱动）。
- 主动推荐：基于画像与场景推荐关联事项（如办完营业执照推荐刻章、开户）。
- 主动总结：长会话结束输出结论与待办清单。

## 6. 可观测、评测与运营

**全链路 Trace**：`trace_id` 贯穿接入层 → Agent 服务 → 模型 → 工具，记录每步输入输出、耗时、token、成本、命中知识、工具结果。

**核心指标**：

- 效果：一次解决率、转人工率、多轮完成率、引用准确率、用户满意度（点赞/点踩）。
- 效率：首 token 延迟、平均轮次、平均步数、工具成功率与失败原因。
- 成本：token 消耗、单次会话成本、模型分布。
- 质量：幻觉/违规拦截率、badcase 数量与闭环率。

**评测体系**：离线评测集（按域维护）+ 发布前回归 + 线上灰度对比 + badcase 自动入集。

## 7. 安全与合规

- 内容安全：敏感词、涉政涉黄涉暴过滤（通过现有平台接口复用 `AiSensitiveWordConfig` 对应的词库与策略）。
- 数据安全：个人信息脱敏（复用现有脱敏规则，经接口获取）、加密存储、最小权限、按租户隔离。
- 权限：Agent/工具/知识按角色与数据范围授权；工具调用以用户身份透传。
- 提示词注入防护：外部内容（检索结果、工具返回）标记为不可信输入，禁止其改变系统指令；工具参数做白名单校验。
- 审计：会话、工具调用、配置变更全量留痕，可导出。
- 合规：回答标注"AI 生成，仅供参考"，重要结论给出官方依据与办理入口。

## 9. 接口设计（概要）

**对外（Agent 服务，SSE）**

```
POST /api/v1/chat/sessions                       创建会话（绑定渠道、Agent 组、用户）
GET  /api/v1/chat/sessions/{id}                  会话详情（含槽位、话题栈）
POST /api/v1/chat/sessions/{id}/messages         发送消息，SSE 流式返回
POST /api/v1/chat/sessions/{id}/interrupt        打断当前 Run
GET  /api/v1/chat/sessions/{id}/runs/{runId}     执行轨迹（调试/回放）
POST /api/v1/feedback                            点赞/点踩/纠错
```

**SSE 事件协议**

```
event: run.start      data: {runId, agentCode, traceId}
event: message.delta  data: {runId, seq, content}
event: thinking       data: {runId, step, summary}      // 可选，前端展示"正在查询…"
event: tool.call      data: {runId, toolCode, args}
event: tool.result    data: {runId, toolCode, status, summary}
event: handoff        data: {from, to, reason}
event: citation       data: {docId, title, clause, url}
event: message.end    data: {runId, usage, finishReason}
event: error          data: {runId, code, message}
event: heartbeat      data: {ts}
```

**管理 API（REST）**：Agent、提示词、工具、知识域、路由规则、模型、评测集、监控报表的 CRUD 与发布，由同一 FastAPI 服务提供，通过管理员角色鉴权。

**工具调用审计**：工具调用统一经过 Agent 服务内的工具网关（参数校验、鉴权透传、限流、留痕），由其转发到业务接口，不另设内部回调接口。

**通用约定**：

- 所有写接口支持 `Idempotency-Key` 请求头，同一 key 24h 内重复请求返回首次结果。
- 错误响应统一结构：`{code, message, traceId}`，`code` 采用 `域.模块.错误` 格式，如 `AC.SESSION.NOT_FOUND`、`AC.RUN.BUDGET_EXCEEDED`、`AC.TOOL.TIMEOUT`、`AC.LLM.UNAVAILABLE`。
- SSE 断线重连：客户端携带 `Last-Event-ID`（即 `run_id:seq`），服务端从断点补发，补发窗口 5 分钟。
- 打断语义：`interrupt` 后当前 Run 在下一个检查点（工具调用前或 token 流间隙）终止，已产生的文本保留并标记 `finishReason=interrupted`；写操作若已提交则不回滚，只返回其最终状态。
- 版本：对外 API 以 `/api/v1` 前缀管理，破坏性变更升 `/api/v2`，旧版至少保留一个迭代周期。

## 9.1 故障与降级策略

| 故障点 | 表现 | 降级方案 |
| --- | --- | --- |
| 主模型不可用 / 超时 | LLM 网关返回 5xx 或超过首 token 超时（3s） | 按 `model_policy` 切换降级模型；仍失败则返回预置话术并提供转人工入口 |
| 知识检索不可用 | 向量库或 ES 异常 | 退化为关键词/FAQ 缓存；仍不可用时明确告知"暂无法查询政策原文"，不编造答案 |
| 业务工具不可用 | 工具超时或熔断 | 查询类：返回已缓存结果（若有）并标注时效；写操作：不执行，告知稍后重试并生成待办 |
| Runtime 实例宕机 | 长连接中断 | 客户端凭 `Last-Event-ID` 重连，负载均衡路由到新实例并从 Run 检查点恢复；无检查点则提示用户重发最后一条消息 |
| 记忆/画像服务不可用 | 读取超时 | 跳过注入，不阻塞对话；记录降级标记到 Trace |
| 审核/敏感词服务不可用 | 无法完成内容检查 | 默认拒绝输出并返回兜底话术（宁可不答，不放行未审内容） |

**灾备**：MySQL 主从 + 每日全量备份；向量库与 ES 可由 MySQL 中的 `knowledge_chunk` 重建；提示词与 Agent 配置版本化存储，支持一键回滚到上一发布版本。

## 9.3 Run 与 Turn 状态流转

```
Run:   queued → running → (waiting_user | waiting_confirm) → running → completed
                       ↘ failed | interrupted | budget_exceeded
Turn:  open → answered | awaiting_clarification → closed
```

- `waiting_user`：Agent 发出澄清问题，等待用户下一条消息后恢复同一 Run。
- `waiting_confirm`：写操作待确认，超时 10 分钟自动取消并记录。

## 10. 与现有系统的集成与迁移

**集成原则**：中台不重写业务，业务系统继续提供接口；Dify 在过渡期作为"能力提供方"被中台调用。

| 阶段 | 动作 |
| --- | --- |
| 并行期 | 中台作为统一入口，Dify chatflow 注册为工具（`dify.chatflow.invoke`），知识库通过同步任务接入知识湖 |
| 试点期 | 选 1 个区客服 + 边聊边办试点，双跑对比指标；提示词迁移到模板中心 |
| 推广期 | 其余区与公共资源交易迁移；总管 Agent 统一路由；下线重复 chatflow |
| 运营期 | 评测驱动迭代，知识统一治理，成本优化（模型路由/缓存） |

**兼容点**：复用现有用户体系、租户、权限、敏感词、文件服务、监控与日志规范（经 HTTP 接口对接）；前端沿用 Vue3 + Element Plus，新增 Agent 管理页面与会话调试台。

**切换与回滚**：每个场景通过接入层路由开关切换"chatflow / agent-center"两种实现，按租户或灰度比例放量；任一指标（一次解决率下降 > 5 个百分点、P95 延迟超标、错误率 > 1%）触发自动切回 chatflow。迁移期间两套实现的会话数据互不混写，仅共享用户身份与知识源。

## 11. 里程碑（阶段划分）

| 阶段 | 交付物 |
| --- | --- |
| M0 基座 | 会话/消息/Run 模型、SSE 流式、单 Agent 执行器、Function Call 工具、提示词模板与版本、Trace |
| M1 记忆与画像 | 分层记忆读写、画像服务与注入、上下文预算与摘要压缩、多轮槽位状态机 |
| M2 协同与工具生态 | Supervisor 路由、Handoff、并行编排、MCP Client、工具权限与审计、确认式写操作 |
| M3 知识协同 | 知识湖、域路由与冲突消解、引用溯源、Dify 知识同步 |
| M4 运营闭环 | 评测集与回归、灰度与 AB、badcase 回流、成本与质量看板、主动服务 |

**阶段验收标准**：

| 阶段 | 验收标准 |
| --- | --- |
| M0 | 单 Agent 完成端到端对话并流式输出；Run 轨迹可在调试台回放；提示词可版本切换 |
| M1 | 多轮槽位收集成功率 ≥ 90%（测试集）；注入画像后个性化用例通过率提升且 token 增量 ≤ 15% |
| M2 | 跨域 Handoff 不丢槽位、不重复提问（抽检 0 次）；写操作确认覆盖率 100%；MCP 工具接入耗时 ≤ 1 人日 |
| M3 | 政策类问题引用准确率 ≥ 95%；同一问题多口径冲突可被正确消解（冲突用例集通过率 ≥ 90%） |
| M4 | 首个试点场景一次解决率不低于 chatflow 基线；badcase 从发现到入评测集闭环 ≤ 3 个工作日 |

**待确认事项的决策截止**：现有平台接口依赖、模型来源（第 12 节）须在 M0 启动前确定，否则 M0 不得开工。技术栈已确定为 Python 单栈。

## 12. 风险与待确认事项

| 风险/待定 | 说明与建议 |
| --- | --- |
| 技术栈（已决策） | 采用 Python 单栈。前提是团队具备 Python 维护能力，若团队主要为 Java 背景，需评估学习成本 |

| 模型来源 | 公有云 API 还是私有化部署（政务数据不出域），直接影响网关与成本设计 |
| 向量库选型 | Milvus / pgvector / ES 向量，取决于数据规模与现有基础设施 |
| 知识迁移成本 | Dify 知识库切片质量参差，需评估清洗与重建工作量 |
| MCP 生态成熟度 | 内部工具优先用 Function Call 注册，MCP 作为扩展通道 |
| 评测基线缺失 | 需尽早与业务共建评测集，否则无法证明迁移收益 |
| 迁移阻力 | 各 chatflow 有历史定制逻辑，需逐场景梳理差异清单 |
| 成本控制 | 多 Agent 协同会增加 token 消耗，需预算与降级策略 |
