# 上下文装配与 LangGraph 剖析

> 日期：2026-10-30
> 方式：容器内 cProfile（ASGITransport，单请求，桩模型）
> 结论：已定位并优化上下文装配；LangGraph 节点本身开销较小，暂无低风险重构收益

## 一、单请求热点变化

| 阶段 | 优化前 | 优化后 |
| --- | --- | --- |
| 单请求总耗时 | 0.284s | **0.153s** |
| `_build_system_prompt` | 0.134s | **0.011s** |
| 知识检索 `search` | 0.124s | **0.003s**（无知识租户早退） |
| `ContextBuilder.build` | ~0.003s | ~0.002s |
| LangGraph `run/_run_inner` | 0.041s | ~0.036s |
| `_build_graph`（构图+编译） | 0.007–0.008s | 0.008s |
| `_decide`（模型调用+步骤+checkpoint） | 0.027s | 0.027s |
| `_act` | ~0.003s | ~0.003s |

## 二、上下文装配

- 最大问题是**无知识空间/无候选切片仍执行 embedding 与向量检索**。
- 已改为早退：无空间、无候选行直接返回。
- 无知识租户检索从约 124ms 降到约 3ms。
- `ContextBuilder` 的近期消息与 prompt 拼装约 2ms，已不是瓶颈。

## 三、LangGraph 节点

- 图构建/编译约 8ms/请求，节点执行本身约 27ms（主要包含模型调用、步骤记录、checkpoint）。
- 节点逻辑没有明显的重复计算；主要成本仍是 DB 事务与模型调用。
- 将图缓存到进程级需要把节点改为 contextvar 派发，改动大、收益约 5%，暂不做，避免破坏恢复/并发语义。

## 四、结论

上下文装配已完成针对性优化；LangGraph 节点层面没有继续拆分的性价比。剩余耗时集中在数据库事务与并发排队，应通过容量扩展解决。
